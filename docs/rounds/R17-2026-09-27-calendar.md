## 做了什么

### 1. 日历邀请 → 访客预登记（`calendar-core.js`、迁移 `0024_calendar.sql`、`public/calendar.*`）

**用法：** 接待人照常在 Google 日历或 Outlook 里约会议，多加一位"与会者"，也就是本租户的日历地址 `cal-xxxxxxxxxxxxxxxx@in.你的域名`。系统读取邀请后给**会议组织者**发一封邮件。组织者点开链接，勾选要给哪些外部访客发邀请，点 **Send invitations**。**组织者不点，谁也收不到任何东西。**

| 环节 | 做法 |
|---|---|
| 收信 | Worker 的 `email()` 处理器（Cloudflare Email Routing 的 catch-all 转给 Worker）。Node 部署用 `POST /api/inbound/calendar`：Bearer 密钥 + `x-envelope-to` 头 |
| 解析 | 自己写的 MIME + iCalendar 解析器，不加依赖。支持 Google 的 multipart、Outlook 的 Windows 时区名和 `VTIMEZONE` 块。读不出时区时按办公室时区，并在邮件和页面上提示 |
| 谁是组织者 | `ORGANIZER` 的邮箱必须是 AccessX 里的在职人员，否则记为"未使用"并写明原因 |
| 谁算外部访客 | 以下都跳过：组织者本人、日历地址本身、AccessX 里已有的人（含停用的）、本租户已验证 SSO 域名下的人。每个会议最多读 20 位 |
| 访客拿到什么 | 和手工 **Visitors → Invite** 走同一段代码（`issueInvite`），只能用所有者给该办公室设定的门（**不能选敏感门**），只在会议开始到结束之间有效。站点有敏感门组时，访客注册后仍需前台批准 |
| 改期 / 加人 | 新版本（`SEQUENCE` 更大）替换还没确认的旧草稿，并重新发链接。重复发送或旧版本会被忽略 |
| 取消会议 | 同一组织者发 `CANCEL`：待确认的草稿作废；已发出但**还没用的邀请自动撤销** |
| 周期会议 | 只用**第一次**（页面上有说明）。如果系列已经开始，会被判为"会议已结束"，这种情况请手工邀请 |
| 限制 | 全天事件不用；30 天以后的会议不用；每租户 24 小时最多 50 封；单封邮件最大 512 KB，最多 50 个 MIME 部分，嵌套最多 5 层 |

**管理界面**（**Visitors → Calendar invitations**）：
- 每个办公室选可开的门，最多 10 个办公室；保存后显示地址和复制按钮。
- **New address** 立即换地址，旧地址马上失效。
- 下面列出最近的日历邀请和状态。

只有所有者能修改；有访客权限的人只能查看。

**谁来担责：** 保存设置的人等于给出了"长期批准"。从日历生成的邀请记为此人创建，审计日志的操作者是 `calendar:<草稿 id>`。如果此人以后失去访客权限，确认时提示"日历邀请已暂停，需要管理员重新保存设置"，并记录 `calendar.failed`。

### 2. 安全设计（详见 `docs/23-CALENDAR.md`）

| 问题 | 做法 |
|---|---|
| 地址被人探测 | **发件人永远收不到任何回复**：未知地址、非邀请、出错一律静默丢弃，不退信。地址有 80 位随机数 |
| 伪造组织者 | `ORGANIZER` 这一行谁都能伪造，**所以不把它当证明**。伪造的结果只是被冒名的同事收到一封"如果不是你发的，忽略即可，没有你什么都不会发生"的邮件。**在他自己的邮箱里点链接才算证明**（和重置密码邮件同一级别的信任） |
| 链接令牌 | 18 字节随机数，只存 SHA-256；一次性，只在草稿待确认、会议未结束时有效；任何错误、过期或用过的令牌都返回同一个 404 |
| 并发双击 | 先用唯一的 `decided_at` 值抢占（CAS + 回读），抢到的那一次才发邀请 |
| Node 入口 | 密钥用恒定时间比较；错误的密钥返回 404 并计入每 IP 限流；服务器出错返回 500，让邮件服务商重试 |
| 审计 | `calendar.configure / rotate / draft / confirmed / declined / cancelled / failed` |
| 个人信息 | 演示重置时清空 `calendar_drafts` |

### 3. SCIM 兼容性回放（`test/scim.conformance.test.js`）
按 Okta 和微软公开的请求格式逐条回放：
- Okta SCIM 2.0 spec test（按顺序）；
- Okta group push（建组带成员、改名、增删成员、删组）；
- Microsoft Entra 的两种 PATCH 风格：
  - **旧版**：`"False"` 字符串、首字母大写的 `Replace`/`Add`、`Remove` 带 value；
  - **`aadOptscim062020`**：不带 path 的 replace、`members[value eq "…"]` 删除；
- 边界情况：不支持的过滤器返回 400 `invalidFilter`，坏 JSON 返回 400，未知 op 被拒绝。

**结果：现有实现全部通过，一行都不用改。** 本轮的产出是这套回归测试，外加变异验证：故意改坏三处，测试都能发现。

### 4. 前台屏幕自动刷新
- 停在 Visitors 页时，每 **20 秒**刷新临时访客列表，新来的标 **new**（橙色）。
- 标签页在后台时，标题变成 **"(2) walk-in · AccessX"**，切回来就复原。浏览器对后台标签页的计时器有节流，最晚约 1 分钟会显示。
- 一次刷新失败不改变任何状态，也不会把所有人都标成"新"。

## 本轮自己踩到并修掉的问题
1. **测试环境读不到密钥。** 测试工具启动服务器后会把环境变量还原，而 `server.js` 原来每次请求才读 `CALENDAR_INBOUND_SECRET`。改为启动时读一次，和其他设置一致。
2. **把站点对象当成站点 id。** `policy.siteForLock` 返回的是站点对象，第一版拿它和 id 比较，所以所有门都被判为"不属于这个办公室"。测试发现后已修。
3. **测试和真实行为不一致。** 我的测试原来预期"确认后访客马上拿到邀请"。但站点有敏感门组时，按 R8 的规则要先经前台批准。这个规则是对的，所以改的是测试：先期望"待批准"，再模拟前台批准。
4. **界面用了不存在的样式。** 标签颜色类 `tag a` 在 CSS 里没有定义，改成已有的橙色 `tag o`。
5. **自动刷新的小毛病。** 一次网络失败会清空"已看过"的记录，下一次刷新就会把所有等待中的访客都标成新的，标签页数字也会虚高。改为失败时什么都不动，失败原因记为控制台警告，不再静默吞掉。
6. **冒烟测试的变量名冲突。** 邮件原文变量叫 `raw`，盖住了同名的请求工具函数。已改名；第一次运行也借此确认了 `email()` 路径已经能生成草稿。

## 需要你做的
1. **部署时**（可选，试点前做完即可）：
   - 在 Cloudflare 上给一个只收信的子域名（例如 `in.doors.你的域名`）开 Email Routing，把 **Catch-all → Send to a Worker** 指到 AccessX；
   - 设 `CALENDAR_INBOUND_DOMAIN`；
   - 跑一次 `npm run doctor`。
2. **试点时问一下客户的 IT：** 他们的 Google Workspace 或 Microsoft 365 是否允许会议邀请外部地址、是否会剥掉 `.ics` 附件。有的公司会，那样邮件就到不了。
3. 如果客户用 Entra ID：不用选 `aadOptscim062020` 这个开关，两种格式都已通过测试。

## 下一轮建议（R18，按路线图）
**访问复核（合规）：**
- 每季度由经理确认谁还应该有门禁权限；没确认的自动提醒，并可一键撤销；

另外建议顺带做：
- 日历邀请的**周期会议**支持"下一次"而不是"第一次"。我倾向于先不做，等试点看真实用法再决定；
- 访客邀请的**批量导入（CSV）**，适合活动和培训日，工作量小。
