## 选型：为什么是 Nuki

| 候选 | 结论 |
|---|---|
| **Nuki Web API** | ✅ 选它。开放的云 API，用 Bearer 令牌；能**列出锁上的键盘密码**，所以 R18 的密码对账可以直接用；可以远程删码；在欧洲办公室很常见 |

## 做了什么

### 1. 接入方式：沿用现有的 vendor 接口

规则、时间表、访客、审批、自动撤销、访问复核、密码对账和审计日志都**不用改**，只多了一个适配器：

| 文件 | 内容 |
|---|---|
| `nuki.js` | Nuki Web API 的 HTTP 客户端（锁列表、授权增删查、开锁、日志） |
| `vendor-nuki-core.js` | 把 Nuki 映射成 AccessX 的门、密码和记录 |
| `support/fake-nuki.js` | 按 Nuki 公开文档写的模拟服务器，**也是异步的**，行为和真服务一样 |
| `vendor-accounts.js` | 用 API 令牌连接，令牌加密保存 |

**没有新的数据库迁移。** 现有的 `vendor_accounts` 表加一行 `kind='nuki'` 就够了。

### 2. 连接

在 Nuki Web 里生成 API 令牌，然后在 **Settings → Lock vendor account → Vendor: Nuki** 里粘贴。

- 令牌用 `SECRETS_KEY` 加密保存，**API 不返回，审计日志里也没有**。
- 连接时会**试着列出第一把锁的密码**。如果令牌没有 `smartlock.auth` 权限，当场拒绝，并告诉你要勾哪些权限，而不是等第一位访客来了才发现。
- 同一个 Nuki 账号不能连到两个 AccessX 租户（409）。
- Nuki 令牌不会过期，但**改 Nuki Web 密码会让它失效**。失效后，下一次访问 Nuki 时账号会变成"需要重新连接"，并通知所有者（和 TTLock 一样）。门页面返回 503，不会显示成"没有门"。

### 3. 几个 Nuki 特有的坑（都已处理并有测试）

| 坑 | 处理 |
|---|---|
| **写入是异步的**：Nuki 返回 204 只代表"请求有效"，不代表码已经生效 | 发码后反复读锁上的密码列表，**确认出现了才把数字给人看**（每 1.5 秒一次，最多 8 次）。始终没出现就报错 `unconfirmed`，什么都不登记；如果它之后才出现，密码对账会把它列为"非系统码" |
| **只设日期不设星期，有效期会被忽略** | 每次都发 `allowedWeekDays: 127`。模拟服务器会记录"有效期被忽略"，测试要求它为假 |
| **键盘码规则**：6 位，只能用 1–9，不能以 "12" 开头，同一键盘不能重复 | 系统自己生成，先读锁上已有的码再避开 |
| **`code` 字段 2024 年从数字改成了数组** | 数字、字符串、数组三种都能读（有测试） |
| **离线的锁收不到新码** | 拒绝发码（409，说明原因）。TTLock 的码离线也能用，Nuki 不行，发出去会给人一个开不了门的码 |
| **离线时撤销** | 登记为"待删除"；**锁重新上线后，自动撤销程序会把它从锁上删掉**，不用专门跑一趟（新测试验证） |

### 4. 界面：每家锁厂做不到什么，直接写在卡片上

锁厂卡片可以选 TTLock 或 Nuki，字段随之切换。连接后卡片下面会用文字列出这家锁厂的限制（由新接口 `GET /api/vendor` 的 `limits` 字段提供）：

- **Nuki：** 需要配对 Nuki 键盘；**不能检测访客到达**（日志只写"键盘"，不写输入了哪个码）；读不到锁报警；每把锁只有最近 50 条记录；写入要等几秒确认；锁离线时不能发新码。
- **TTLock：** 有效期按整点；时段码开始后 24 小时内必须用一次；远程开门和远程删码需要网关。

这样客户在选锁之前就能看到差别，不用等出错才发现。

## 本轮自己踩到并修掉的问题

1. **Nuki 的错误信息到不了操作员。** 通用错误处理会把所有 409 改写成"有冲突，请重试"。于是"这把锁没有键盘"之类的原因被吞掉了。现在 Nuki 的请求错误原样传给界面（有测试检查原文）。
2. **离线锁本来会收到码。** 第一版只检查了有没有键盘，没检查在不在线。Nuki 云会接受请求，但码要等锁上线才同步，访客拿到的是一个开不了门的码。现在拒绝，并说明原因。
3. **没有权限的令牌能连上。** 连接时只读了账号和锁列表，只读令牌也能通过，要到第一次发码才报错。现在连接时就试着读一次密码列表。
4. **测试写法问题（不是产品问题）：** 锁列表缓存 60 秒，令牌失效后第一次读门列表仍然成功。和 TTLock 行为一致，可以接受；测试改成用一个真正访问 Nuki 的操作来触发。

## 限制（诚实说明）

- **只在模拟服务器上测过**，没有真实的 Nuki 账号和锁。模拟服务器照公开文档写，但文档和实际行为可能有出入。
- `25-NUKI.md` 第 6 节列了 6 项**第一家真实 Nuki 站点之前必须做的检查**，用一把锁、一个键盘、一个网桥大约 20 分钟。
- 没有做 OAuth2 和 webhook（需要 Nuki 合作伙伴账号），目前没有功能依赖它们。

## 需要你做的

1. **如果试点客户用的是 Nuki：** 在安装当天先按 `25-NUKI.md` 第 6 节检查一遍（约 20 分钟），尤其是第 1 项：码在有效期之前和之后都**开不了门**。
2. 选锁时可以把卡片上的"限制"给客户看。**需要"访客到达通知"的客户，建议继续用 TTLock。**
3. Nuki 令牌请用专门的管理员账号生成，并告诉客户：**改这个账号的密码，门禁系统就会断开**（所有者会收到通知）。
