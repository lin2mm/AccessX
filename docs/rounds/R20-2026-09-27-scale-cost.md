# R20：规模与成本（2026-09-27）

**一句话：** 按 200 门 / 5,000 人 / 100 租户压测，找到并修掉两个问题：一个性能瓶颈（Node 混合负载快 7.5 倍），一个**只在 Cloudflare 上出现的严重故障**（并发读写时约 11% 的请求返回 500）。另外发现冒烟测试的\"日志无错误\"检查从 R15 起就是瞎的，已修好。成本结论：**约 70–120 个租户以内整个账号每月 5 美元，之后每个租户每月约 0.07 美元**；定价不用考虑 Cloudflare 费用。数据库每周自动导出到 R2，导出的副本能通过完整的恢复测试。

- 时间：19:29–20:16（路线图计划 19:30–20:10，超出约 6 分钟，都花在追查 500 故障上）
- 提交：`478ae45`、`4f279df`、`ba751c4`、`c0a9978` + 文档提交

## 3. 找到并修掉的问题

### 3.1 性能：时区校验每次都新建 `Intl` 对象

剖析发现编译接口大部分时间花在反复检查\"这个时区名是否有效\"上，每次都新建一个 `Intl.DateTimeFormat`。加了缓存以后：编译 57 → 9 ms（基准测试），夏令时提醒 11.7 → 1.1 ms，混合负载 10.7 → 80 次/秒。

### 3.2 严重：Cloudflare 上并发读写时约 11% 请求返回 500

**现象：** 混合负载阶段有 177 个请求返回 500，日志是 `Cannot perform I/O on behalf of a different request`。

**原因：** Cloudflare Workers 有一条规则：一个请求不能等待另一个请求发起的 I/O。我们有三处\"合并重复工作\"的写法：多个请求同时要读快照时只让一个去加载，其他人 `await` 同一个 promise；TTLock 令牌刷新；冷启动初始化。在 Node 上这是正确的优化，在 Workers 上就会出错。

**修复：** 新文件 `store/shared-wait.js`。在 Workers 上，等待方不再 `await` 别人的 promise，而是用自己的定时器轮询一个\"完成了没有\"的标志（每 5 ms）。等太久（10 秒）就自己做。在 Node 上照旧直接 `await`。三处都改了。

**证明**（同样的条件：全新 D1、全新 Worker、2,000 人、连着 Nuki）：

| 版本 | 混合负载中的 500 | 日志中的错误 | 吞吐 |
|---|---|---|---|
| 旧写法（直接 await） | **144 / 1,342** | 318 | 66.5 次/秒 |
| 新写法 | **0 / 1,638** | 0 | 81.5 次/秒 |

之后 5,000 人 / 100 租户的完整压测也是 0 个错误。

**为什么之前没发现：** Node 测试里没有这条规则；Worker 冒烟测试是一个接一个顺序发请求，没有并发；而本来能看见这些错误的日志检查恰好是坏的（见 3.3）。

**诚实说明：** 这个故障**只在全新启动的实例上**出现。我先用\"已经跑过一阵的实例\"做对照，结果旧写法也不出错，差点误判。后来按原始条件重来一遍（全新 D1 + 重启）才稳定复现，才有了上面的对照表。三处共享等待里具体是哪一处触发的，没有逐一拆开验证，三处都改了。

### 3.3 冒烟测试的日志检查从 R15 起没起作用

wrangler 输出带颜色，`[ERROR]` 实际上是 `[` + 颜色码 + `ERROR` + 颜色码 + `]`，所以原来的匹配**一次都没匹配上过**。拿 3.2 失败时的日志测试：旧检查找到 0 行，实际有 318 行。R15–R19 报告里写的\"wrangler 日志无新错误\"因此不能算数。

**修复：** 先去掉颜色码再匹配，也匹配 `[wrangler:error]`。**验证：** 修好后在全新环境跑冒烟测试，35/35，日志确实 0 个错误，所以之前的轮次没有漏掉真的错误。再把失败日志注入进去，检查报出 318 行，冒烟测试失败，说明它现在能拦住问题。

## 4. 数据库每周自动导出到 R2

原来需要人记得每周手工跑 `npm run backup -- d1`。现在（`backup-export-core.js`）：

- 定时任务每周一次、在安静时段（默认 UTC 17 点 = 悉尼凌晨 3–4 点）把整个数据库导出成 SQL，边导出边 gzip，写到 R2 的 `d1/accessx-<时间>.sql.gz`，保留最近 8 份（两个月）。
- `npm run backup -- verify` 现在也能读 `.sql.gz`，**R2 里的每份副本都能做完整恢复测试**：能否加载、完整性、表/索引/触发器、每个租户的审计链、加密密钥是否匹配。
- 平台接口：`GET /api/platform/backups`（列出副本，只有文件名、大小和行数，没有数据）、`POST /api/platform/backups/run`（立即导出一份，上线后第一次验证用）。只有平台令牌能用，租户所有者令牌得到 401。
- 没绑定 R2 桶时，`GET /api/platform/doctor` 会警告。

**实测：** 16,317 行 → SQL 4.3 MB → gzip 0.5 MB，330 ms。在 workerd 上从 R2 下载那份副本做恢复测试：13 个租户、5,076 人，全部通过。

**为什么没按路线图用 Workflow：** 导出 16,000 行只要 0.3 秒，普通定时任务就够了。而且导出时是流式压缩，内存里只放压缩后的数据（约为原文的 1/8），100 万行时约 30 MB，在 128 MB 限制以内。数据量大到这个程度时再换 Workflow。

**R2 桶没有写进仓库的 `wrangler.jsonc`：** 如果绑定的桶不存在，部署会直接失败。上线时先建桶再加绑定，命令在 `12-GO-LIVE.md` §4。

## 5. 每个租户的 Cloudflare 成本（`40-BILLING.md`）

按典型试点租户算（50 人、10 门、每月 300 个访客、约 1,000 次改动、前台开着访客页）：

- **5 美元的套餐能覆盖约 70–120 个租户。** 最先用完的是 Worker CPU，最坏情况下是 Durable Object 运行时长。
- **超出以后每个租户每月约 0.07 美元**（最坏情况约 0.13 美元）。
- 最大的成本来源是**每 15 分钟一次的定时任务**：每个租户每天唤醒 Durable Object 96 次，即使什么都没变。超过约 100 个租户时，可以跳过没事要做的租户，或者改成每 30 分钟。
- 一个 D1 数据库最多 10 GB（硬上限）。按每个租户每年 1–2 MB 算，够几千个租户用一年。
- 真正的每租户成本在别处：短信、邮件服务、Stripe 手续费、安装和支持时间。门数下限（例如 5 门）就是为了覆盖这些。

## 6. `npm run nuki:check`

照 `ttlock-check` 的样子写的真机检查，第一次去客户现场时用：

- **只读模式：** 列出每把锁，报告是否在线、有没有键盘、电量、约 200 个授权位用了多少、能不能读日志。
- **加上 `--write <锁号>`：** 用和生产环境**同一套代码**发一个 1 小时的码，等 Nuki 确认，打印数字，删掉，再确认已经删除。发码后和删除后都要在键盘上实际输一遍。
- 用模拟 Nuki 测过：离线锁和没有键盘的锁都会报失败；只读令牌会报\"读不了码\"；错误的令牌会报 401；报告里不会打印令牌。

## 限制（诚实说明）

- **所有 Cloudflare 数字都是本地 workerd 测的。** 本地的 Durable Object 和前端 Worker 在同一个 isolate 里；生产环境还要加上到 D1 主库的往返延迟。CPU 时间是估计的，上线后看 Cloudflare 后台的实际数字。
- **R2 导出不是一致性快照。** D1 不支持跨查询的快照，导出期间如果有写入，副本可能有轻微不一致。所以放在安静时段跑，恢复测试也会重新校验审计链；校验不过就用 Time Travel。AccessX 自己不加密（R2 静态加密），桶必须保持私有。
- **`GET /api/users` 没有分页**（5,000 人时 656 KB）。第一个超过约 1,000 人的租户之前要做分页。
- 撤销报告每次读全部行（5,000 人时 5,236 行，费用约为零），暂时不改。

## 需要你做的

1. **上线时：** `npx wrangler r2 bucket create accessx-backups`，把绑定加进 `wrangler.jsonc`，部署后调一次 `POST /api/platform/backups/run`，下载那份副本跑一次 `npm run backup -- verify`，把结果记进 `12-GO-LIVE.md` §6 演练记录。
2. **建 D1 时选靠近客户的位置**（澳大利亚：`--location oc`，建之前先确认当前可用的位置代码）。
3. 第一次去 Nuki 客户现场：先跑 `npm run nuki:check`，再加 `--write` 发码测试，把 `--json` 生成的报告放进现场记录。
