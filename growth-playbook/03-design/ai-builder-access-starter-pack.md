# Free Builder Pack：从AI演示到可审查的现场访问流程

2026-09-28｜可复用文档草稿，未发布。不包含可运行SDK、生产API、硬件认证或真实测试结果。以下ID、数据、事件全部为合成示例，不允许用于开真实门。中文文档＋英文字段便于builder理解；实施仍需单独批准。

## 1. 用十分钟决定是否值得继续

适合：你为具体物业/空间/维护场景开发软件或AI终端，有合法授权人，希望保留合适的原锁，愿意先验证少量普通门型。

不适合：没有现场负责人、要求通用门型保证、要求只凭语音自动开门、无法保留安全应急方式、公共逃生系统未经专项审查、希望供应商免费代工研发或先发货后付款。

你不需要现在购买任何工具/锁。先填写：
- 终端场景/国家/门型：____
- 谁拥有或有权管理门、谁批准安装：____
- 已选软件平台/实际设备及固件：____
- 当前最贵的一个失败案例：____
- 哪个事件触发授权、哪个事件结束授权：____
- 断网/卡阻时谁到场、如何保证通行：____
- 付款方、进口方、售后责任：____

未知项留空，不用AI猜参数。不给我们密码、API key、住户身份证、完整住址或真实门码。

## 2. 最小业务流程，不增加一个全能平台

授权业务系统产生事件 → 校验租户/门/人/时间窗 → 判断是否需要人工批准 → 下发适用操作 → 收集执行证据 → 告知结果/未知 → 异常工单 → 现场安全处置。

AI可用于解释记录、补齐问询、建议下一步。**授权决定在可审计的规则与负责人员，不在模型自由文本。**模型不能自行扩大门范围、延长时间窗或替换批准人。

先把这条链人工跑通，才讨论SDK/MCP/自动化模板。原型模拟器里成功不代表实物成功。

## 3. 拟议数据契约（不是当前TTLock接口）

| 英文字段 | 意义 | 使用规则 |
|---|---|---|
| tenant_ref | 业务租户伪名ID | 每个请求服务端授权；不是由客户端自报就可信 |
| site_ref / door_ref | 场所与门的内部引用 | 通过授权映射，不把地址写进公开日志 |
| subject_ref | 获授权的人/角色 | 不收集无必要PII；任务负责人不一定有门权限 |
| source_event_id / source_version | 业务事件与版本 | 去重/乱序保护；旧事件不能恢复已取消的授权 |
| valid_from / valid_until | 授权时间窗 | 明确时区/DST，拒绝不确定时间；不能默认永久 |
| requested_action | 请求意图 | 示例只允许模拟或人工评审；不公开通用unlock入口 |
| approval_ref | 必要审批记录 | 绑定具体对象/动作/期限；不能复用一次审批放行所有动作 |
| execution_state | 请求/执行证据状态 | requested / confirmed / failed / unknown / manual_review |
| evidence_source / observed_at | 证据来源与观察时间 | 状态有新鲜度；请求时间不冒充设备观察时间 |
| fault_category | 可观测症状分类 | 原因不确定就unknown，不假装机械确诊 |
| case_ref | 支持/RMA工单号 | 脱敏输出，不能凭工单号取得开门权限 |

不要把上述schema误写成所有平台的真实返回字段。生产字段需与具体API/设备映射且最小化存储。

## 4. 一个完整的合成例子

场景：授权管理员给某维护人员预约访问。不是租客租住权，也不是因付款状态变化撤销通行。

1. 合成预约evt-demo-001/v1要求在已明确时区的一个小时窗口内访问door-demo-A。
2. 系统核验tenant-demo-A确实获授权管理该门，维护人员身份和时间窗有授权来源。
3. 策略生成待审批任务；审批未通过前不向设备发送写操作。
4. 审批后，模拟连接器返回“请求已受理”，界面仍为requested。
5. 若获得适用路径的设备执行确认且数据新鲜，更新为confirmed；这仅确认对应授权操作，不证明门物理安全锁住。
6. 预约取消产生v2；若设备离线，显示撤销待确认/需人工处理，不能显示“已撤销”。
7. 授权现场责任人按批准的应急流程处置；不重复撞击电机，不自动解锁，不误伤其他合法用户访问。
8. 后到达的v1不能覆盖v2。恢复联网后按授权和接口实际能力核对残留权限。

模拟结果标记simulation=true，只存在文档里的预期行为，尚无程序执行。

## 5. 可交给开发者/合作方评审的验收表

见[12个合成场景](../05-system/ai-builder-synthetic-cases.csv)。覆盖正常流程、取消离线、重复乱序、跨租户、提示注入、语音身份不足、状态陈旧、供应链成本、支持数据脱敏和付费到期。

验收证据不只看LLM回复“完成”。至少区分：业务状态、API结果、设备执行结果和物理状态；不同层的未知不能被下一层默认填为成功。

## 6. 对接常用builder工具时的边界

- AI编程工具：可阅读本草稿来生成原型，但所有生成代码仍须安全审查和测试。本轮未生成/改动App。
- GitHub：可以承载文档和测试计划；本轮未发布到公共仓库、未联系任何项目维护者。
- Supabase等后端：租户授权须由可信服务端强制实施，不能只有前端筛选。
- 自动化工具：先从通知、创建待审批工单开始；重试消息不代表允许重复物理动作。
- MCP：只读检索和合成诊断建议优先；协议不会自动提供正确的业务权限和实物安全。
- 分析/客服：只传白名单摘要；不录制真实门码输入，不上传原始锁详情中的密钥。

## 7. 现场设置清单与责任交接

购前：原锁/门型/安装许可/应急方式核验 → 配件与网络清单 → 完整成本与责任说明。

到货：SKU/批次确认 → 门开着做原锁手动基线 → 依批准说明安装校准 → 有人在场验证关门负载与机械应急 → 数据/权限检查 → 授权负责人签收。

异常：记录直接观察，不给过度确定根因 → 支持分级 → 有资格人员维修或按合同RMA → 复核恢复。

这不是安装手册，也不替代实际型号的厂商步骤和当地安全法规。没有合格门型与应急方案不放行。

## 8. 可选服务，不捆绑购买

- 免费：本文、合成场景、未知项自检、成本模型说明。
- 待验证的付费：限定范围部署评审、标准接入和售后工作区。
- 可选硬件：只在门型/型号/合规通过后报价，先预付、出货前付清，按合同履约/退款。

不买硬件也可使用独立软件；不因商业订阅未续费禁用基础开门。任何24/7人工应急承诺需有真实团队与预算。

## 9. 你对这份材料的反馈应是什么

不要只问“喜欢吗”。请指出：哪个真实项目需要它？哪部分现有平台已解决？还缺什么才敢部署？你愿为哪一项付费，谁有预算？哪项责任不愿承担？这些答案决定是否继续，而不是下载次数。
